# Future: Doctor Opus Trial / Light Mode на Claude Haiku 5.5

**Дата решения:** 19 ноября 2026 года.  
**Статус:** подтверждённая владельцем продуктовая идея для будущей коммерческой версии / backlog. **НЕ внедрять сейчас, не менять default модели или биллинг.** Приоритет — довести W4 → W5 → G-WORKSTATION до клинической и эксплуатационной приёмки.

## Решение владельца

Claude Haiku 5.5 показала достаточно полезные ответы при пробах в материнском Doctor Opus. Это **не только учебный бот по интерфейсу**: в будущем продукте она может самостоятельно отвечать на **простые клинические вопросы** в честно обозначенном `Trial / Light` режиме, а также помогать новому пользователю освоить рабочие процессы Doctor Opus. Бенчмарки не означают клиническую эквивалентность с Sonnet/Opus для сложных случаев; не утверждать обратное и не обесценивать Haiku.

**Покупатель подписки** получает экономичный режим для первых шагов, упражнений и лёгких клинических вопросов. Для сложной диагностики, выбора терапии, ответственных решений, полноценного консилиума, сложных изображений — `Clinical / Pro` с действующими Sonnet 5.5, Opus 5.5, Gemini и профильными инструментами. **Не смешивать стоимость Light и Pro, не запускать дорогие модели незаметно.**

Пример коммуникации пользователю:
> «Light / Trial — Claude Haiku 5.5: быстрые ответы на простые вопросы, изучение интерфейса, учебные клинические сценарии. Для сложных и ответственных случаев используйте Clinical / Pro с более мощными моделями.»

**Это предложение, не утверждённые коммерческие тарифы.** Стоимость подписки, срок триала, включённые обращения и переход между планами будут решены позже.

## Цели

- Позволить врачу изучить **настоящий интерфейс** Doctor Opus без дешёвой имитации функциональности.
- Использовать Haiku 5.5 как рабочую малую модель для: кратких справочных вопросов, объяснений терминов, навигации по модулям, структуры уже подтверждённых записей, учебных сценариев и подходящих низкорисковых клинических запросов.
- Использовать синтетические случаи и предварительно проверенные демонстрационные результаты для обучения полному процессу «случай → документы → специалист → лекарства/источники → протокол»; не заставлять Haiku **притворяться** инструментом КТ/МРТ/ЭКГ или полным Opus-консилиумом.
- Переключение на Clinical / Pro должно быть простым и объяснимым, при **явном выборе врача** с показом разницы по функциональности/стоимости.
- Отдельно обозначать **фактическую модель ответа** и статус: «ответ Light (Haiku 5.5)», «демонстрационный пример» либо «Clinical / Pro», чтобы человек не перепутал эти режимы.

## Безопасность и маршрутизация

- Haiku в Light **может отвечать на низкорисковые клинические вопросы**, это не только распорядитель. Это **исключение, изолированное от действующего клинического маршрута**: в нынешней рабочей станции Haiku остаётся Copilot/вспомогательным инструментом, Sonnet — обычным клиническим консультантом, Opus — сложным.
- Для неотложных симптомов, высоких рисков, индивидуального подбора доз и терапии, серьёзной клинической неопределённости, мультиморбидности, медицинских изображений и консилиума — сообщить об ограничениях и предложить режим Clinical / Pro, **не выдавая ответ Haiku за полноценный клинический анализ**. Короткое сообщение может быть высокорисковым; «QTc 610 мс», «K+ 6.8» и одышка с гипоксемией — не «лёгкие вопросы».
- Роутинг риска должен опираться не только на количество слов и не только на самооценку Haiku; для high-risk требуется проверяемое правило/сигнал/ограничение и возможность ручного выбора Pro.
- Даже в Light можно отвечать на общие образовательные вопросы; не требовать оплачиваемый полный консилиум для ответа «что такое PR-интервал?».
- Не выдавать отсутствие найденного DDI за безопасность; не выдумывать объективный осмотр, диагнозы, нормальные анализы, проверенные источники, результаты детекторов или назначения.
- В учебных сценариях — только синтетические/разрешённые демонстрационные данные, заметная маркировка `TRAINING`, отдельное пространство без смешения с рабочими клиническими случаями. Не допускать случайного переноса учебного заключения в карту реального пациента.
- Если пользователю позднее разрешат работать с реальными данными в Light, это требует отдельного решения по приватности, ограничениям и медицинскому качеству, а не автоматически наследует возможности учебного режима.

## Экономика и продуктовая упаковка

- Учитывать настоящий `usage.cost` провайдера, выводить понятный бюджет/лимиты, считать удельную стоимость на ответ и учебную сессию. Не обещать постоянные тарифы по данным на ноябрь 2026 года.
- Лимиты по числу запросов, токенам/месяц, длине истории, аудио/изображениям и затратам — по будущему тарифному плану.
- Не допускать незаметного перехода на Sonnet, Opus, платные STT/vision/consilium через действие из Light. При необходимости показать причину и возможность осознанно включить Pro (проверить право доступа и бюджет).
- Не усложнять ядро новой системой подписок до готовности G-WORKSTATION; при разработке использовать небольшую изолированную feature-flag / entitlement прослойку и существующие компоненты.
- Никакой обязательной связи с будущим аватаром: аватар — отдельно отложенная, необязательная опция.

1. После W5/G-WORKSTATION провести аудит существующего Copilot, Specialist и Cost routing, изучить продуктовые права доступа. Не дублировать уже реализованное.

3. Подготовить на синтетике независимые тесты: Light простая клиника/навигация, опасные короткие вопросы, попытки обойти платный Pro, правильное отображение используемой модели, сохранность границ учебных и рабочих случаев, отсутствие лишнего биллинга.
4. Не делать вывод, что малый mock-тест доказывает безопасность Haiku; перед коммерческим включением нужны параллельные клинические оценки ответов Haiku/Sonnet/Opus, врачебная экспертная разметка, лимитированные реальные API-тесты **только с разрешённым бюджетом**.
5. Отдельный Draft PR для реализации после решения владельца. **Этот документ — сохранение идеи, а не разрешение на код, merge, платные запросы или деплой.**

## Отношение к другим решениям

- Не менять существующее решение: **Haiku не участвует как клинический специалист в текущем Consilium**. Отвергнутый экспериментальный PR #101 не должен быть внедрён.
- PR #102 (качество/стоимость основных моделей) и PR #105 (будущая прямая транскрипция AssemblyAI STT-3.7 для диктовки и Ambient) — отдельные задачи. Они не должны блокироваться Trial/Light.
- Главный приоритет: работающая клиническая станция врача, а не функция коммерческого обучения.

**Критерий успешности будущей функции:** человек на доступной подписке действительно учится и получает полезные ответы на несложные вопросы по низкой себестоимости; ограничения очевидны; серьёзные медицинские задачи переходят в полноценный клинический режим только осознанно; ни клиническое качество, ни данные пациентов, ни биллинг не страдают.
