# Doctor Opus Clinical Intelligence — Roadmap V2: довести рабочую станцию врача

**Дата:** 17 ноября 2026. **Статус:** утверждённое направление планирования; реализация этапов проверяется отдельно.  
**Исходный репозиторий:** [vasiliys961/consilium](https://github.com/vasiliys961/consilium).  
**Порядок без исключений:** **вначале рабочая станция врача (C1–C14) → её сквозная клиническая и эксплуатационная приёмка → только потом самостоятельный Opus Integration Hub (H0–H5).**

## 0. Критерий продукта

Doctor Opus должен быть клинически полезным и интуитивным: врач в одном рабочем месте загружает данные, формулирует вопрос текстом или голосом, получает клинический разбор/мнение специалиста, добавляет исследования, проверяет лечение и источники, формирует редактируемый протокол, печатает/передаёт его и продолжает случай. Технические настройки, номера портов, выбор внутренних моделей, статусы адаптеров и журналы — **только в разделе администратора**.

**Сквозное определение «готово»:** «открыть/создать случай → загрузить материалы → задать вопрос → получить содержательный ответ → выполнить нужный работающий модуль → вернуть подтверждённый результат → проверить назначения → сохранить/распечатать/передать документ → открыть случай снова». Зелёный CI проверяет инженерную целостность, но **не** подтверждает реальную работу врача или клиническую валидность.

### Границы разработки

- Только отдельные `chatgpt/*` ветки и PR в `chatgpt-dev`; Preview `127.0.0.1:3207`. **Не трогать рабочие `main` и `3107`, исходный `vasiliys961/doctor-opus`, отдельные Radiology/ECG/US/Genomics/Translator, продакшен, секреты или сохранённые случаи.**
- Никаких повторных «подготовить → подтвердить → снова подготовить». Врач делает необходимое действие один раз, а система сообщает фактический результат либо понятную причину сбоя.
- Существующее переиспользуем через адаптер. Не заменять функциональность архитектурой, не добавлять новый сервис ради уже решённой задачи.
- Продолжать развитие по существующему [ROADMAP.md](ROADMAP.md), [PROJECT-STATE.md](PROJECT-STATE.md), [NEXT-STEPS.md](NEXT-STEPS.md) и [AGENTS.md](../AGENTS.md), но **очередь и условия перехода в новый этап определяет этот V2**. Старые выполненные этапы не открывать повторно.
- Medical Translator — дополнительный аксессуар, не обязательное ядро; ветку `chatgpt/c11-translator-case-return-20261116` не сливать без решения владельца.
- Реальные персональные данные не использовать для CI/тестов; передача за пределы разрешённого контура только по применимой правовой основе, политике провайдера и после проверки минимизации данных и согласия. Никакого автоматического платного обращения без решения врача.

## 2. Практическая последовательность завершения рабочей станции (БЕЗ Hub)

### Этап W1 — C13: нормальный разговор и выбор специалиста (сразу следующий)

1. Проверить на `3207` реальные сценарии «Что умеет Doctor Opus?», «Найди ЭКГ», «Болит грудь», «Одышка и результаты обследования», свободный неструктурированный вопрос.
2. Без лишних платных вызовов различать справку по приложению, консультацию врача, открытие инструмента, работу с текущим случаем; при неуверенности — универсальный врач, с возможностью ручного выбора.
3. Специалист принимает текст, речь и документы PDF/DOCX/XLSX/TXT/CSV; бинарные картинки/DICOM через предусмотренный разбор случая. Не терять ввод при переходе; пользователь выбирает «продолжить разговор» или «создать/пополнить случай».
4. Устранить конкретные лаги и неверные переходы; не разрабатывать новый общий framework, если имеющийся маршрут работает.
5. **Приёмка:** одна задача с голосом + документом → профильный/универсальный специалист → содержательный ответ → продолжение без потери контекста; справка о возможностях без LLM.

### Этап W2 — C13-B/C: агент выполняет один инструмент и сохраняет результат

1. Научить Copilot проверять **фактическую**, а не декларативную доступность модуля: статус входных форматов, возможность обработки, границы расходов/приватности.
2. Первый целевой адаптер выбрать из **проверенных** специалистов/протоколов — не блокировать работу нестабильной Radiology.
3. По решению врача выполнить одно типизированное действие; наблюдать завершение и ошибки; вернуть результат с provenance, source SHA, версией модели/инструмента, фактической или неизвестной стоимостью.
4. Добавить сохранение новой редакции без перезаписи решений врача; затем два модуля в простой цепочке и отмена.
5. **Приёмка:** «голос/текст → предложенный план → подтверждение → реальное выполнение → результат → сохранить → открыть снова». Не считать запуском только открытие страницы.

### Этап W3 — C14: Ambient-протокол на готовых RU/Global

1. Одна кнопка «Записать приём», отдельное согласие пациента; безопасный старт/стоп/отмена, без автозаписи.
2. Запись → STT → редакция транскрипта → извлечение структурированных полей с привязкой к исходной фразе/времени и неопределённой роли говорящего, если диаризация ненадёжна.
3. Явная проверка лекарств, доз, чисел, единиц, отрицаний и неопределённых признаков; не выдумывать витальные данные/осмотр.
4. Из черновика создавать **исходный RU или Global** протокол, редактировать, утверждать, сохранять и печатать. Проверить русскую запись и затем один другой поддерживаемый язык.
5. **Приёмка:** запись вымышленного приёма → корректные критические факты → утверждённый редактируемый протокол → повторно открыть случай.

### Этап W4 — единый клинический маршрут и уже существующие функции

1. C1/C2: синтетический пациент → жалобы, вопросы, документы → консилиум → новые данные → обновлённое решение без потери старых материалов.
2. **Рекомендации:** объединить существующие поиски через отдельный `Guidelines Adapter`; два режима: самостоятельно искать рекомендации и получать релевантные источники в разборе. Не переписывать оба поисковика и не изобретать третий.
3. **Назначения:** предложенные лекарственные варианты автоматически проходят проверку взаимодействий, доз/контекста; врач редактирует и утверждает свою схему. Альтернативные планы не считаются одновременным приёмом.
4. **Документы:** вернуть уже существующие **печать, «поделиться протоколом», проекты рецептов** из родительского Doctor Opus, если они подтверждены тестами. Медицинское решение и юридически действительный рецепт — разные вещи.
5. **ЭКГ и УЗИ:** получить результат именно от установленного работоспособного модуля и сохранить его с исходниками/масштабом. Неподдерживаемые форматы ЭКГ и живой поток аппарата не объявлять решёнными.
6. Генетика и RU/Global: возврат и версии; основные действия доступны из случая без перехода в технические настройки.
7. **Приёмка:** один сквозной синтетический случай, все подтверждённые компоненты дают реальный результат, итог редактируется, печатается/передаётся и повторно открывается. Не требовать полного Radiology для приёмки остальных модулей, но явно оставить его открытым долгом.

### Этап W5 — C3/C12, источники и эксплуатационная приёмка

1. Контрольный набор клинических сценариев (в том числе полипрагмазия, почечная/печёночная недостаточность, QTc, дозы, беременность где применимо, аллергия, опасные диагностические пропуски). Независимо фиксировать ожидаемое, выявленное, пропущенное и ложное.
2. Проверить источники и цитирование по руководствам: дата/популяция/показание/страница, международная база + применимые локальные документы.
3. C4/C5/C7/C8/C9/C10: мобильная передача, OCR, личная библиотека, импорт/экспорт и обновление без потери данных. Дорабатывать только найденный клинически значимый пробел.
4. Небольшой контролируемый набор реальных модельных вызовов (после отдельного разрешения расходов), замер задержки/цены/стабильности; ошибки исправлять по факту, не расширяя модельный зоопарк.
5. **Приёмка:** документированные результаты тестов и реальные браузерные действия, безопасное сохранение, отсутствие известных блокирующих отказов на заявленных сценариях; синтетика не приравнивается к независимой клинической валидации.

### Этап W6 — вернуться к отложенной Radiology до окончательной приёмки станции

1. Надёжный автоматический старт и проверка готовности дочерней Radiology, один пользовательский вход без npm/портов.
2. Один обезличенный DICOM-срез → подготовка → **одно** осмысленное разрешение → один платный Gemini → фактический ответ; никаких петель. Потом серия КТ/МРТ, правильный выбор кадров/окна.
3. Заключение и покрытие исследования, источник/ограничения, врачебная правка и возврат в случай; повторное открытие.
4. Не смешивать работу PNG/X-ray/ECG с доказанным анализом CT/MRI. Без удачного сквозного теста модуль остаётся **не готов**.
5. **Приёмка:** работающий контрольный DICOM и успешная повторная сессия после обновления; показать врачу только клинический результат или простую понятную ошибку.

### Gate G-WORKSTATION — только после него начинаем Hub

Следующие условия должны выполняться одновременно:
- C13 навигация/специалисты/выполнение подтверждённого инструмента, C14 RU/Global Ambient и клинический маршрут действительно работают в браузере.
- Ключевые интегрированные модули имеют подтверждённый «вход → анализ → результат → сохранение»; оставшиеся неподдерживаемые сценарии явно помечены и не блокируют станцию.
- Случай, материалы, библиотеки, документы, печать и перенос не теряются после обновления/сбоя.
- Для лекарств и клинических решений есть измеренные контрольные результаты и список ограничений.
- Врач работает без команд и технических подтверждений; платные вызовы выполняются контролируемо.
- В отдельном отчёте владельцу показаны подтверждённые ограничения/долги. **Только явное решение владельца переводит Hub из планирования в разработку.**

## 3. Очередь ближайших PR: не возвращаться к уже сделанному

1. **W1-Browser:** приёмка текущего PR #58 и исправления строго по найденным дефектам Copilot/специалистов.
2. **W2-One-Tool:** типизированный адаптер к уже работающему специалисту/протоколу, полный возврат в один случай.
3. **W3-Ambient-RU:** реальная запись, STT, редактируемый RU протокол и сохранение.
4. **W3-Ambient-Global:** второй язык, проверка ролей, чисел и отрицаний.
5. **W4-Guidelines:** один общий слой доступа к *двум существующим* источникам рекомендаций.
6. **W4-Documents-Medications:** печать/поделиться/проекты рецептов + проверка предложенных назначений, без дублирования функций родительского `doctor-opus`.
7. **W4-ECG-US-Genetics:** по одной проверяемой интеграции с фактическим ответом и возвратом.
8. **W5-Clinical-Acceptance:** независимые синтетические критерии, браузерная приёмка библиотеки, архивов, мобильного сканирования и обновлений.
9. **W6-Radiology-Recovery:** изолированное устранение блока 3210 и настоящий ответ по DICOM, когда владелец вернёт задачу в работу.
10. **G-WORKSTATION:** отчёт о готовности рабочей станции, перечень оставшихся неподдерживаемых функций и решение владельца.
11. **H0 Integration Hub — только ПОСЛЕ пункта 10 и нового разрешения.**

**Правило продвижения:** один PR = один клинический результат; CI + браузерная приёмка; не копать новые технические детали бесконечно. По завершении этапа переходить к следующему по очереди.

## 4. Будущий Opus Integration Hub — отдельный проект ПОСЛЕ станции (НЕ строить сейчас)

### Что это будет

Независимый адаптивный интеграционный модуль для подключений к:
- медицинским системам и БД: МИС/ЭМК, ЛИС, PACS/RIS, FHIR, HL7, DICOM/DICOMweb, REST/OpenAPI, файлы/CSV;
- внешним анализаторам и детекторам, которые можно запускать законно и технически: ECG, CT/MRI, УЗИ, лаборатории, изображения, локальные ONNX/Python workers, разрешённые исследовательские API;
- инструментам и агентам через стандартизированный поддерживаемый интерфейс: **MCP**, OpenAPI, webhooks/очереди; Codex, Grok Bot, OpenClaw, Hermes и другие — **только после проверки конкретной версии и её действительно доступного API/MCP**;
- данным медицинских приборов: Web Serial/USB CDC, WebUSB/WebHID при совместимости, UVC/`getUserMedia`, HDMI/SDI→USB video capture, BLE/GATT, Ethernet/Wi-Fi, локальный файл прибора, DICOM отправка, DICOMweb/DIMSE через шлюз, HL7/IEEE 11073/ASTM только для поддерживаемых аппаратов.

**Независимость:** отдельный репозиторий или пакет, без импорта в исполняемое ядро Consilium до приёмки; выключен по умолчанию, не запускает сервисы/USB/агентов при старте. Сбой Hub не должен менять/ломать случай или анализ. Copilot — лицо для врача; Hub — скрытый слой транспорта и преобразования данных. Начать с синтетических mock/read-only данных. Клиническое ядро подключать лишь через версионированный ограниченный контракт после отдельного согласования.

### Что реально найдено в исходном `vasiliys961/doctor-opus` (аудит кода 17.11.2026)

### Будущие адаптеры и общий медицинский контракт

1. **H0 (позже):** изолированная спецификация `HubCapability` / `HubInput` / `HubResult` / `HubAudit` (типы, версия, формат, устройство, измерения/единицы, происхождение, источник SHA/идентификатор, лицензия, стоимость, разрешение/ошибка). Threat model и каталог устройств без доступа к пациентским файлам.
2. **H1:** read-only mock-адаптеры FHIR Observation, ECG CSV и DICOM study; отмена, таймаут, проверки размеров, границы форматов.
3. **H2:** нормализация FHIR/HL7/LOINC/UCUM, DICOM и CSV с сохранением исходных единиц и ссылок на источник. Никакого прямого write-access к рабочим БД.
4. **H3:** один разрешённый реальный внешний детектор, один тестовый MCP-инструмент в sandbox; явные ограниченные полномочия, платные вызовы только по согласию, запрет автоматического исполнения произвольных команд и утечек.
5. **H4:** один конкретный медицинский прибор с протоколом производителя и проверкой частоты дискретизации/калибровки, затем UVC/video/file-import. Web Serial/WebUSB не работают одинаково в Safari и Chromium; альтернативный локальный bridge только с разрешением владельца. Управление прибором/воздействие на пациента — вне этой задачи.
6. **H5:** опциональный, выключенный по умолчанию мост к Consilium после независимой приёмки; проверка «Hub unavailable → Doctor Opus продолжает работать», версионирование и подтверждённый возврат результата в случай.

### Обязательный Privacy Gateway будущего Hub

- Исходные документы/DICOM, Patient ID, ФИО, ключи и полный анамнез — локально в разрешённом контуре по умолчанию.
- Для разных форматов — DICOM tags + надписи в пикселях, PDF metadata/OCR, FHIR/HL7 идентификаторы, текст/аудио, малые даты/косвенные признаки и журналы доступа. Псевдонимизация не равна гарантированной анонимности.
- Минимально необходимый набор данных, одобренный получатель, законное основание, отдельное разрешение на передачу, scoping API, лог только без PHI, журнал преобразования и контроль source hash.
- Внешним агентам не давать SSH/root, полный диск, секреты, доступ к БД пациентов или прямую запись в историю. Read-only sandbox и проверка действий с последствиями.
- Не обещать универсальную совместимость устройств/стандартов: нужна спецификация конкретной модели, режим сигнала, фильтры и эталонная проверка измерений.

**ЗАПРЕТ НА ПРЕЖДЕВРЕМЕННУЮ РАЗРАБОТКУ:** H0–H5 — документированные будущие задачи. **До прохождения G-WORKSTATION не создавать Hub runtime, адаптеры, пакеты, MCP-серверы, драйверы, USB-сервисы или новые зависимости в Consilium.** Даже после gate нужен отдельный запрос владельца на старт проекта.
